| ADR-04 | Money is `NUMERIC(14,2)` in the DB and `BigDecimal` in Java. Rates/percentages are `NUMERIC(6,3)`. Quantities are `NUMERIC(12,3)`. Rounding is centralised in `common/util/Money` (HALF_UP, scale 2). | SRS §3, prompt §2. |

## D. Phase 3 decisions (as built, 2026-10-25)

These follow the Phase 3 instruction. Where the instruction left a detail open, the choice below is the most restrictive reasonable one, and it is reported here rather than applied silently.

| ID | Topic | Decision | Reason |
|---|---|---|---|
| P3-01 | Role model | Exactly three active roles: `SUPER_ADMIN`, `ADMIN`, `USER`. V12 retires `SALES_MANAGER`, `SALES_EXECUTIVE`, `FINANCE` and `PARTNER` (`active=false`, rows kept) and drops the empty `user_roles`/`role_permissions` tables. A guard aborts V12 if `role_permissions` holds rows. No user is elevated: existing users (none existed) map SA > ADMIN > USER, otherwise USER. | Phase 3 instruction; forward-only, no privilege elevation. Supersedes D-23 and the 6-role table in the old `API_DESIGN.md §2`. |
| P3-02 | Role codes vs names | Codes are immutable (JPA `updatable=false` plus DB trigger `trg_roles_code_immutable`). Authorization never reads display names. Names are unique case-insensitively among active roles (partial unique index), 2–60 characters, whitespace collapsed. | Instruction: "Never use editable display names for authorization". |
| P3-03 | Permission storage | Per user, in `user_module_permissions` (a row means Read; plus write/delete/export/approve and data scope) and `user_action_permissions` (module actions). Role templates (`role_permission_templates`) are applied on create and on role change; a role change **resets** permissions to the new template (audited with before/after). | Single source of truth; editable per user as required. |
| P3-04 | Super Admin access | Computed (all modules, all supported flags, all actions); no rows are stored and the matrix is not editable (`422 SUPER_ADMIN_PERMISSIONS_FIXED`). | "Full access that doesn't depend on stored rows". |
| P3-05 | Delegation | Only a Super Admin can change permissions (`USER_MANAGEMENT:MANAGE_PERMISSIONS` is Super-Admin-only and not grantable). Nobody can change their own permissions or role. A non-Super-Admin with User Management write can create/edit **User-role** accounts only and cannot assign another role. `ROLE_MANAGEMENT` is Super-Admin-only. A USER-role account can never hold `USER_MANAGEMENT`. | Instruction: restrict delegation to Super Admin. |
| P3-06 | Action placement | `VIEW_INTERNAL_B2C` → PRODUCTS (B2C columns on the price sheet; later also estimates). `INTERNAL_B2C` module READ gates the internal twin documents (Phase 8). `MARK_PAYOUT_PAID` → PAYOUTS. `REVERSE_PAYMENT` → PAYMENTS. `MANAGE_USERS` = activate/deactivate. `MANAGE_SETTINGS` = commercial policy settings (Phase 13). Approve is offered on PARTNERS (apply tier reviews) and LEADS (acknowledge). Delete on INVOICES means cancel. | The instruction lists the actions but not their modules; these follow the source actions. |
| P3-07 | Data scope | Stored per module (SELF/TEAM/ALL) and resolved by `DataScopeService`. There is no record ownership (D-30) or team model, so **SELF and TEAM resolve to "no records"** instead of silently widening to ALL. Templates and existing rows use ALL. The UI never picks a scope silently: a newly granted scope-capable module requires an explicit choice. API clients that omit `dataScope` get ALL (the column default). | "Don't fabricate teams. Don't auto-grant ALL. Deny where scope can't be enforced." |
| P3-08 | Admin default template | As specified: Dashboard R; Partners, Leads, Products, Estimates, Invoices, Payments RW; Payouts R; Reports R. Admin has **no** User Management, Settings, Internal B2C or Audit access by default; a Super Admin grants them per user. | Instruction default template. |
| P3-09 | Sessions | Access JWT HS256, 15 min, carries only `sub`, `sv` (session version), `role` (informational), `iss`, `iat`, `exp`, `jti`. The principal and permissions are re-read from the DB on every request, so permission changes, deactivation and password changes apply immediately. Refresh tokens: 7 days, random 256-bit, stored as SHA-256, rotated on every use; replaying a rotated token revokes the whole family. Cookie `iotiq_rt`: HttpOnly, SameSite=Strict, Path `/api/v1/auth`, Secure except in the dev profile. Refresh/logout require `X-Requested-With`. | ADR-07 plus immediate revocation. |
| P3-10 | Login protection | Generic `401 INVALID_CREDENTIALS` for unknown user and wrong password (constant-time BCrypt comparison against a dummy hash for unknown users). Lockout after 5 consecutive failures for 15 minutes (`423`). A disabled account is reported (`403 ACCOUNT_DISABLED`) only after the correct password. | Account-enumeration resistance. |
| P3-11 | Passwords | BCrypt cost 12. Policy: 12–128 characters, at least one letter and one digit, not equal to the email. New accounts and the bootstrap Super Admin must change the password at first sign-in; until then every API except `/auth/me`, `/auth/change-password`, `/auth/logout`, `/auth/refresh` returns `403 PASSWORD_CHANGE_REQUIRED`. A password change revokes all other sessions. | Instruction. |
| P3-12 | Emails | Stored trimmed and lower-cased; uniqueness and login are case-insensitive. | Avoids duplicate accounts differing only by case. |
| P3-13 | ADR-06 refinement | Internal product fields are served by the same `/api/v1/products` endpoints using a separate DTO (`InternalProductResponse`) only when the caller holds `PRODUCTS:VIEW_INTERNAL_B2C`; everyone else gets `ProductResponse`, which has no B2C fields. B2C-name search is only applied for internal callers. Separate `/internal/**` routes remain the plan for the B2C twin documents (Phase 8). | Same security property with less duplication; tested in `InternalB2cSecurityIT`. |
| P3-14 | ADR-12 refinement | The UI uses the original application's design tokens and component classes (`styles/globals.css`) with Radix primitives (dialog) instead of generated shadcn/ui components. Tailwind stays available for layout. | Keeps the IOTIQ look exactly; fewer generated files. |

## F. Phase 5 decisions (as built, 2026-10-25)

| ID | Topic | Decision | Reason |
|---|---|---|---|

| P5-02 | GSTIN masking (revised 2026-10-25) | A GSTIN embeds the holder's PAN in characters 3–12, so an unmasked GSTIN defeats PAN masking. Audit snapshots, log statements, error responses and list/search results never contain a full GSTIN. GSTIN and PAN are not searchable. On update GSTIN follows P5-06 (null keeps, "" removes). | P5-04 | No delete | There is no delete endpoint (BR-P10). `DELETE /partners/{id}` returns 405. Deactivation is a status change. | BR-P10. |
| P5-05 | Data scope | SELF/TEAM scope on PARTNERS returns no rows and a 404 on detail (P3-07). | No record ownership exists yet. |
| P5-06 | PAN / GSTIN / bank on update | `null` keeps the stored value, `""` removes it, and any other value replaces it. Users who can't see the values get empty fields with "Remove the stored …" checkboxes. A masked value sent back is rejected by format validation, without echoing it. | Lets masked users edit a partner without wiping or re-entering data they can't see. |
| P5-07 | Formats | PAN `AAAAA9999A`; GSTIN `99AAAAA9999A9Z9` pattern; IFSC `AAAA0XXXXXX`; bank account 9–18 digits (spaces and dashes removed); phone 7–15 digits; agreement date not in the future (Asia/Kolkata); notes ≤ 2000 characters. All are optional except name and category. Values are upper-cased and trimmed. | Catch typos before they reach payouts. The client mirrors the rules; the server is authoritative. |
| P5-08 | Audit | `PARTNER_CREATED`, `PARTNER_UPDATED` (changed keys only), `PARTNER_STATUS_CHANGED` and `PARTNER_TIER_REVIEWED`. PAN, GSTIN and bank account are always masked in audit snapshots. Change detection compares the **unmasked** values, so a new PAN/GSTIN/account with the same visible tail is still saved and audited (it appears as masked → masked). | "Never store secrets in audit logs", extended to sensitive personal data. |
| P5-09 | Tier review apply | The client sends the previewed `(partnerId, action, toLevel)` items. The server locks the partners (`SELECT … FOR UPDATE`), recomputes each one, and rejects the whole batch with `409 TIER_REVIEW_STALE` if any result differs. Each applied change writes a `partner_tier_reviews` row with the actor and sets `last_tier_review_on`. | No partial or outdated tier changes. |
| P5-10 | Review population | A bulk preview covers every non-Inactive partner. A single-partner preview (from the detail page) reviews that partner whatever its status. | §3.1 says "all non-Inactive" for the bulk review. A deliberate single review is an explicit choice. |
| P5-11 | Progress | Progress to the next tier is measured against the next tier above the **assigned** tier (BR-P13), so a partner whose revenue already qualifies shows 100% until a review upgrades them. | Matches what the fee rate actually is. |
| P5-12 | Deferred | `partner_code` and address fields (D-16), the fee statement CSV (Phase 11), linked-record lists (Phases 6–11; the detail page explains this, with no placeholder data), and the scheduled tier review (D-07, manual only). | Out of Phase 5 scope. |
| P5-13 | Grace after a manual tier change | A manual tier or programme change by a Partners approver clears `downgrade_grace`. The grace period belongs to the tier it was granted on (§3.1), so the next review below the new tier starts a fresh grace period instead of stepping down at once. Edits that leave the tier alone keep an existing grace period. | Found in browser verification: a partner moved to Elite by hand was immediately offered a step-down. |
| P5-14 | Integrity-violation logging | `DataIntegrityViolationException` logs only the constraint name and SQL state, not the driver message. PostgreSQL's "Failing row contains (…)" would otherwise write PAN, GSTIN or bank details to the server log. | "Do not log credentials", extended to sensitive identifiers. |

## G. Phase 6 decisions (as built, 2026-10-25)

| ID | Topic | Decision | Reason |
|---|---|---|---|
| P6-01 | SLA calculation | `LeadSla` reproduces the source's `leadSla`: hours rounded half up (so the acknowledgement breach starts at 48.5 h), unacknowledged Won/Lost leads have no clocks, the estimate clock uses the earliest-dated estimate of any status and the acknowledgement date in Asia/Kolkata, and closed leads without estimates stop the estimate clock. Targets come from company settings. The `slaBreach` list filter expresses the same rules in SQL (`LeadMetricsRepository.slaBreachedIds`); an integration test checks that the two agree. | §4.1 golden vectors (`LeadSlaTest`). |
| P6-02 | Stage rules (D-04) | Any stage to any stage, except that moving a Won or Lost lead to a different stage needs `LEADS:APPROVE` (`403 STAGE_REOPEN_NOT_PERMITTED`), through either `PATCH /stage` or the edit form. Every change writes `lead_stage_history` (`STAGE_CHANGED`, from, to, optional reason ≤ 500, actor). Creating writes `CREATED`; acknowledging writes `ACKNOWLEDGED`. The UI locks the inline select of closed leads for users without approve, and asks for confirmation and an optional reason before a reopen. | Accepted D-04 option. |
| P6-03 | Conflict check (D-05) | Runs on every create and update. A conflict is another live (not deleted) lead with the same non-empty last-10 phone digits, a different partner and `protection_until >= today`. The lead is saved with `conflict = true`; the response names the partner with the longest-running protection. The stored flag is refreshed on each save; detail responses also show the partner protecting the phone right now. | Accepted D-05 option; BR-L6 boundary. |
| P6-04 | Soft delete (D-26) | Migration V14 adds `deleted_at` / `deleted_by` and partial indexes. Delete needs `LEADS:DELETE` and is refused with `409 LEAD_HAS_DOCUMENTS` ("Mark it Lost instead") while any estimate, invoice, payment or internal B2C document references the lead. Deleted leads are hidden from lists, detail (404), conflict checks and partner lead counts; their history and audit rows stay. | Accepted D-26 option; keeps FK integrity. |
| P6-05 | Acknowledge | Needs `LEADS:APPROVE`. Locks the partner's current tier commission into `locked_fee_percent` (later tier or rate changes don't touch it), sets protection to today + `lead_protection_days`, moves NEW → REGISTERED (other stages unchanged) and records who acknowledged. The row is locked (`SELECT … FOR UPDATE`) so a double click can't acknowledge twice; the second call gets `409 LEAD_ALREADY_ACKNOWLEDGED`. | BR-L5. |
| P6-06 | Partner after acknowledgement | Once acknowledged, the referring partner can't be changed (field error on `partnerId`). The source allowed it, which would leave a fee rate locked from another partner's tier and protection credited to the wrong partner. | Protects the locked fee. **Approved deviation from the source (2026-10-25).** Before acknowledgement, users with Leads write may change the partner; afterwards both the API and the form refuse it. No reassignment workflow in Phase 6. |
| P6-07 | Lead number and client email | `lead_number` and `client_email` exist in the schema but stay unused until D-16 is approved. | D-16 still needs approval. |
| P6-08 | Data scope | SELF/TEAM scope on LEADS returns no rows and a 404 on detail and commands (P3-07). | No record ownership (D-30 is free text). |
| P6-09 | Audit | `LEAD_CREATED`, `LEAD_UPDATED` (changed keys only, including the conflict flag), `LEAD_STAGE_CHANGED` (with reason), `LEAD_ACKNOWLEDGED` (stage, locked fee, protection date) and `LEAD_DELETED` (snapshot). | Phase 3 audit conventions. |
| P6-10 | Partner lead list | The partner detail page lists the partner's leads with the same inline actions, through `GET /leads?partnerId=` and only for users with `LEADS:READ`. "New lead" there pre-selects the partner. | Replaces the Phase 5 placeholder for leads. |

| P6-13 | Acknowledging closed leads | Won and Lost leads can't be acknowledged: the API answers `422 LEAD_CLOSED` ("Won and Lost leads can't be acknowledged.
