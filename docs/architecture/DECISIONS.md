| ADR-04 | Money is `NUMERIC(14,2)` in the DB and `BigDecimal` in Java. Rates/percentages are `NUMERIC(6,3)`. Quantities are `NUMERIC(12,3)`. Rounding is centralised in `common/util/Money` (HALF_UP, scale 2). | SRS §3, prompt §2. |
| ADR-05 | **Server is the calculation authority.** The client sends only inputs. Shared calculation rules are mirrored in TS only for live preview, and the server result is authoritative. Golden test vectors live in one JSON file used by both JUnit and Vitest. | Prompt rules 7, 9-security. |

## D. Phase 3 decisions (as built, 2026-10-25)

These follow the Phase 3 instruction. Where the instruction left a detail open, the choice below is the most restrictive reasonable one, and it is reported here rather than applied silently.

| ID | Topic | Decision | Reason |
|---|---|---|---|
| P3-01 | Role model | Exactly three active roles: `SUPER_ADMIN`, `ADMIN`, `USER`. V12 retires `SALES_MANAGER`, `SALES_EXECUTIVE`, `FINANCE` and `PARTNER` (`active=false`, rows kept) and drops the empty `user_roles`/`role_permissions` tables. | P3-02 | Role codes vs names | Codes are immutable (JPA `updatable=false` plus DB trigger `trg_roles_code_immutable`). Authorization never reads display names. | P3-06 | Action placement | `VIEW_INTERNAL_B2C` → PRODUCTS (B2C columns on the price sheet; later also estimates). `INTERNAL_B2C` module READ gates the internal twin documents (Phase 8). `MARK_PAYOUT_PAID` → PAYOUTS. `REVERSE_PAYMENT` → PAYMENTS. `MANAGE_USERS` = activate/deactivate. `MANAGE_SETTINGS` = commercial policy settings (Phase 13). The one permission change: migration V16 sets `modules.supports_approve = true` for INVOICES, so the existing generic APPROVE flag can be granted on Invoices. **Nobody is granted it by the migration;** Super Admin has it by definition, and others only if an administrator grants it. Rows marked **Needs decision** are GST or accounting-policy questions that couldn't safely be inferred. Those rules are **not implemented**; the app refuses or leaves the case out instead of guessing.

### GST treatment (D-21, as approved)

| ID | Rule | As built |
|---|---|---|
| P9-G1 | Supplier registration | `company_settings` holds the legal name (`company_name`), registered address, `state_code` (new) and `gstin`. DB checks: the GSTIN format and that its first two digits equal `state_code`. Edited at `/settings` (`PUT /settings/gst-registration`, Settings write). GSTINs are checked for format, a valid state code and the mod-36 check character. Issue is refused (`422 SUPPLIER_REGISTRATION_INCOMPLETE`) until the name, address, state and GSTIN are all set. On issue, the supplier name, address, GSTIN and state are copied onto the invoice, so later changes never alter issued invoices. |
| P9-G2 | Customer details | Billing name, address, billing state (optional) and customer GSTIN (optional, validated the same way). The billing name and address are required to issue. The partner's GSTIN is a protected field (`PARTNERS:VIEW_PARTNER_SENSITIVE`), so it is **never copied** into an invoice; the writer enters the billing GSTIN. |
| P9-G3 | Place of supply | Stored explicitly as a state code plus a basis: `RECIPIENT_LOCATION`, `DELIVERY_LOCATION`, `INSTALLATION_SITE` or `OTHER`. It is **never derived from the billing state**. Both are required to issue. Without them the draft carries no tax type and no tax, and the editor says so. |
| P9-G4 | Tax type | Supplier state = place of supply → intra-state (CGST + SGST); otherwise inter-state (IGST), as in IGST Act ss. 7–8. Intra-state supplies in a union territory without a legislature (04 Chandigarh, 26 Dadra & Nagar Haveli and Daman & Diu, 31 Lakshadweep, 35 Andaman & Nicobar, 38 Ladakh) use **UTGST** instead of SGST. Delhi, Puducherry and Jammu & Kashmir levy SGST. State list: 36 current codes; retired codes 25 and 28 and the special codes 96/97/99 are excluded. |
| P9-G5 | Rounding and amounts | All `BigDecimal`, HALF_UP to the paisa, **per line**: taxable = r2(qty × rate × (100 − discount%)/100); intra: CGST = SGST/UTGST = r2(taxable × GST%/200); inter: IGST = r2(taxable × GST%/100); line tax = sum of its components; line total = taxable + tax. Invoice totals are sums of the lines; discount amount = Σ line amounts − Σ taxable. Each line stores taxable value, GST %, CGST, SGST/UTGST, IGST, total tax and line total; the invoice stores CGST, SGST, IGST, taxable, GST and grand totals. Estimates keep their D-25 document-level rounding and are never recalculated. |
| P9-G6 | Explicit confirmation | When the treatment can't be decided reliably, issue needs a confirmation from a user with `INVOICES:APPROVE`, with a written note (`POST /invoices/{id}/confirm-tax`); otherwise `422 TAX_CONFIRMATION_REQUIRED`. Reasons: billing state missing; place of supply differs from the billing state; customer GSTIN registered in another state than the billing state; basis `OTHER`; a converted invoice whose tax type differs from the estimate's. The confirmation stores a key over supplier state, billing state, GSTIN, place of supply, basis, tax type and the estimate's choice. Any change to these inputs invalidates it (it is cleared on save), and issue re-checks the key. Audited as `INVOICE_TAX_CONFIRMED` with the reason codes and the note. |
| P9-G7 | Snapshots | Issue recomputes tax from the stored lines and the current registration, then freezes everything: supplier snapshot, billing details, place of supply and basis, tax type, UTGST flag, confirmation, per-line amounts and totals. An issued invoice's treatment is never re-evaluated: responses show the stored values. |

**Needs decision (not implemented; the app doesn't guess):**
1. **e-Invoicing (IRN/QR):** mandatory above the turnover threshold. Needs the company's turnover status and an IRP integration decision.
2. **Reverse charge:** not applicable to the current product range as far as the source shows. Confirm whether any supply can fall under RCM.
3. **Exports, SEZ and other zero-rated supplies, and place of supply outside India (codes 96/97):** not supported. Such invoices can't be created.
4. **Composition scheme, cess, bill of supply for exempt items:** not supported.
5. **Round-off of the invoice total to the rupee:** not applied (totals are to the paisa). Confirm the policy.
6. **Per-line rounding:** implemented as described in P9-G5 (the approval asked for per-line amounts). Please confirm it is the accounting policy you want.
7. **Credit and debit notes:** required before paid invoices can be cancelled or corrected (P9-04). Planned with Phase 10.

### Decisions as built

| ID | Topic | Decision |
|---|---|---|
| P9-01 | Conversion (`POST /invoices/from-estimate`) | Needs `INVOICES:WRITE` and `ESTIMATES:READ`; both data scopes must be ALL. **Refusals:** deleted estimate → `409 ESTIMATE_DELETED`; Draft or Rejected → `409 ESTIMATE_NOT_CONVERTIBLE`; a live (draft or issued) invoice already exists → `409 ESTIMATE_ALREADY_INVOICED`; deleted lead → `409 LEAD_REQUIRED`. **Allowed:** Sent, Accepted, or Invoiced when every earlier invoice was cancelled. The estimate row is locked for the conversion, and a partial unique index (`ux_invoices_live_estimate`) backs this up, so concurrent conversions create exactly one draft. **Copied:** lead, partner, bill-to, discount, fee, notes and every line (description, HSN/SAC, unit, quantity, rate, GST %, product, and the B2C snapshot for the internal twin only), plus the billing name only. The estimate becomes Invoiced (locked for edit and delete, P8-08/09), with an `ESTIMATE_STATUS_CHANGED` audit row; its stored values and totals are not touched. |
| P9-02 | Converted drafts | Keep the estimate's commercial values: lead, bill-to, discount, fee and lines must be omitted or unchanged (`400`, "comes from estimate …"). Only the billing details, place of supply, due days and notes can be edited. Tax is recalculated per line for the place of supply. The preview and the invoice show the comparison with the estimate (taxable, GST and total differences, and a changed tax type) before issue. Discarding a converted draft restores the estimate's previous status. |
| P9-03 | Lifecycle and immutability | **Draft:** editable with `INVOICES:WRITE`, discarded (soft delete) with `INVOICES:DELETE`. **Issue** (`INVOICES:WRITE`): requires a complete supplier registration, billing name and address, place of supply and basis, lines and any required confirmation. Optional `expectedGrandTotal` returns `409 TOTALS_CHANGED` if the total moved. Issue assigns the number, sets invoice date = today (Asia/Kolkata) and due date = today + due days (default 15 from settings, 0–365), copies the supplier, writes the internal B2C twin `INT-INV-…` and moves the lead to Won (BR-V3; issuing for a Lost lead needs `LEADS:APPROVE`, D-04). **Issued/Cancelled:** lines, prices, taxes, customer details and number can't change. The API returns `409 INVOICE_ISSUED` / `409 INVOICE_CANCELLED`, and V16 triggers reject updates of those columns, any line change and any delete in the database. Optimistic locking (`version`) on every action. |
| P9-04 | Cancellation | `POST /invoices/{id}/cancel` with `INVOICES:DELETE` and a reason (1–500 characters), audited as `INVOICE_CANCELLED`. A draft → `409 INVOICE_DRAFT` (discard instead); already cancelled → `409 INVOICE_CANCELLED`. **Refused while any payment or partner payout references the invoice** (`409 INVOICE_HAS_PAYMENTS`), so cancellation can never leave payments or payouts inconsistent. Cancelling paid invoices needs the reversal and credit-note handling of Phase 10. The number stays used; the estimate stays Invoiced and may be converted again because no live invoice remains. The DB allows only the cancellation columns to change on an issued invoice. |
| P9-05 | Numbering | `INV-YYYY-NNNNNN` from `DocumentNumberService.next("INV")`: an atomic upsert on `document_sequences(prefix, year)` inside the issuing transaction. YYYY is the calendar year (Asia/Kolkata) of the issue. Unique (DB index), assigned only on issue, immutable (DB trigger), never reused (cancelled numbers stay). A failed issue rolls the counter back. Verified with concurrent issues: unique and contiguous. Drafts are identified by their UUID; `ck_invoices_draft_number` enforces draft ⇔ no number. |
| P9-06 | Payment status (BR-V6) | Derived, never stored: Unpaid, Partially paid, Partially paid · overdue, Overdue, Paid (₹0.50 tolerance), Cancelled; none for drafts. Paid = sum of recorded payments (Phase 10 records them). List filter values: UNPAID, PARTIALLY_PAID (both partly-paid states), PAID, OVERDUE. |
| P9-07 | Direct invoices and pickers | `POST /invoices` with `INVOICES:WRITE`. Leads come from `GET /invoices/lead-options` (Invoices write, no Leads read): at most 50 live, non-Lost leads; only `id, leadNumber, clientName, partner{id, name}`; search on lead number, client and partner name only. The Invoices scope must be ALL and, when the user has Leads access, so must the Leads scope. Products come from `GET /products/options`, which now also accepts `INVOICES:WRITE` (minimum fields; B2C name and rate only with `PRODUCTS:VIEW_INTERNAL_B2C`). Create and edit apply the same eligibility to ids sent directly (`400 leadId` / `lines[i].productId`). Changing a line's GST % from the product's (or the saved line's) rate needs `INVOICES:APPROVE` (`400 lines[i].gstPercent`). A fee override still needs `PARTNERS:APPROVE` and a reason (D-13). |
| P9-08 | Partner-safe vs internal | Partner-safe: `/invoices/**` responses, the printable invoice, the CSV export and the audit rows (built only from partner-facing columns). Internal: `/internal/invoices/{id}` and `/{id}/document` need `INTERNAL_B2C:READ` + `INVOICES:READ` and exist only once issued (draft → `409 INTERNAL_COPY_NOT_READY`). The preview's `internal` block needs `PRODUCTS:VIEW_INTERNAL_B2C`. Integration tests scan every partner-safe output for B2C names, B2C prices and the twin number. |
| P9-09 | Audit | `INVOICE_CREATED`, `INVOICE_CONVERTED`, `INVOICE_UPDATED` (changed keys only; an unchanged save writes nothing), `INVOICE_TAX_CONFIRMED`, `INVOICE_ISSUED` (number, dates, supplier state, tax type and amounts), `INVOICE_CANCELLED` (reason), `INVOICE_DRAFT_DELETED`, and `GST_REGISTRATION_UPDATED` for settings. GSTINs are recorded masked (`••` + last 3 characters); change detection compares the unmasked values. No B2C data, no passwords and no tokens. |
| P9-10 | Documents | The server renders "TAX INVOICE" as HTML (supplier and customer blocks with GSTINs, place of supply and basis, HSN/SAC, taxable value, rate, CGST + SGST/UTGST or IGST per line, totals). Drafts print as "DRAFT INVOICE · not a tax invoice"; cancelled invoices carry a CANCELLED stamp. The internal copy is stamped INTERNAL ONLY. Printing and PDF are done by the browser, as for estimates (D-15: server PDF before production). |
| P9-11 | Data scope | Invoices use the INVOICES scope; SELF/TEAM resolve to no records (404 on detail), as for estimates (D-30). |
| P9-12 | Deferred | Payments, receipts, reversals and credit notes (Phase 10); partner payouts (Phase 11); e-invoicing and the GST items under "Needs decision"; server PDF (pre-production); emailing invoices. |
